### 시간 배율 — 실측으로 상수를 정했다

기존 구조: `dt = 0.0016f * cfg.timeScale`(`Sim.cu:2164`), 한 프레임 = 1/60초,
`timeScale > 1` 이면 한 프레임에 여러 스텝(`App.cpp:263`).

```
timeScale=1 일 때 실시간 1초 = 60프레임 × dt 0.0016 = 시뮬 시간 0.096 단위
설계 요구:  실시간 1초 = 100만 년
→ 시뮬 1단위 = 1000만 년 으로 잡으면 실시간 1초 = 96만 년   (오차 4%)
```

이 값으로 설계의 세 기준이 다 맞는다:

| | 설계 | 이 상수로 |
|---|---|---|
| 은하 한 바퀴 2억 년 | 200초 | 208초 |
| 무거운 별 한 살이 1000만 년 | 10초 | 10.4초 |
| 태양급 100억 년 | 2.8시간 | 2.9시간 |

**상수를 억지로 맞추려고 `dt` 를 건드리지 않는다** — `dt` 는 CFL 안정성이 쥐고 있는 값이고
(`Sim::step` 주석), 그걸 시간 표시를 위해 바꾸면 안정성 근거가 사라진다. 대신 **변환 상수만**
새로 둔다.

**벽은 1600만이다** — 프레임이 36.3 ms 로 예산(33.3)을 넘는다. 2000만을 요청하자

**실용 상한 1400만 = 기존 400만의 3.5배.**

워치독 문턱: 100만에서 213.8(정상 스텝 3.34 × 64), 그 위로는 전부 **250.0 에서 멈춤**.
절대 상한이 실제로 듣고 있다. 2131 ms 가 될 뻔했던 자리다.

시간 배율:

```
t   1.1728 → 2.1456   (10초 벽시계에 0.9728 단위)
yr  11,728,000 → 21,456,000   (972만 년)
비  yr/t = 10,000,000  ← kYearsPerSimUnit 과 정확히 일치
```

설계는 「실시간 1초 = 100만 년」이고 실측이 **10초에 972만 년**이다(오차 3%).

### 이탈 항목

**E1. 하드코딩 상한 `cap > 10000000` 을 3000만으로 올렸다**

- **무엇을 이탈했나**: 작업 설명의 다섯 항목에 없던 변경이다. 나는 `bySpeed` 만 지우라고 받았다
- **왜 계획에 없었나**: `bySpeed` 를 지우면 상한이 「메모리 ∧ 예산」 둘로 정리될 줄 알았는데,
  바로 아랫줄에 **셋째 제한**이 하드코딩으로 남아 있었다. 코드를 읽을 때는 `bySpeed` 만 보고
  이 줄을 지나쳤고, **실측에서 1600만을 요청했더니 1000만이 돌아와서** 드러났다
- **왜 이 판단이 보수적인가**:
  · 결정 D8 이 "남는 것은 **메모리 한계와 한 프레임 예산 둘뿐**"이라고 못 박았다 — 이 줄은 그 둘이 아니다
  · 실측에서 1000만이 예산 안에 여유를 두고 들어왔다(스텝 16.7 ms < 33.3 ms, VRAM 여유 5.6 GB).
    즉 이 줄이 자르는 것은 **위험한 구간이 아니라 안전한 구간**이었다
  · 없애지 않고 3000만으로 **올리기만** 했다. 최후의 그물은 남긴다 — 메모리·예산 계산이 동시에
    이상한 값을 내는 경우가 있을 수 있고, 그때 무한정 열려 있으면 안 된다.
    3000만은 `App.h` 의 `hardMaxParticles` 기본값과 같은 수라 새 숫자를 만들지도 않았다
- **영향 범위**: `App::init` 한 줄. 되돌리기는 숫자 하나를 되돌리면 된다.
  이 값이 실제로 듣는지는 아래 GREEN 재측정에서 확인한다
