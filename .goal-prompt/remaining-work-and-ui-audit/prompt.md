D:\Project\Nbody (Stardust, CUDA 입자 시뮬레이터) 에서 남아 있는 작업을 전부 끝내고,
모든 UI 기능을 하나씩 전수조사해 고칠 것을 고쳐라. 먼저 남은 작업을 목록으로 적어
어디까지 왔는지 눈에 보이게 만든 다음 시작한다.

남은 작업은 셋이고 진단은 이미 끝나 있으니 원인부터 다시 조사하지 마라. 첫째, 발광성운을
켜는 것이다. 가스 알갱이 30만 개가 지금 화면에 한 픽셀도 안 그려진다 — `Sim.h` 의
`nebulaK` 가 0 이기 때문인데, 0.02 로 켜면 화면이 온통 주황이 되고(실측: 따뜻한 색 94.4%,
푸른색 0.02%, 켜진 픽셀 4.8만→11.4만, fps 60→46.7) 다섯 배 낮춰 0.004 로 해도 90.3% 로
거의 그대로다. 밝기 기준이 상위 5% 백분위수라 가스를 어둡게 하면 기준도 함께 내려가
비율이 안 바뀐다. 그러니 세기를 만지지 말고 이온화 문턱을 넣어라 — 실제 HII 영역은
스트룀그렌 반경으로 경계가 뚜렷한데 지금 코드는 별빛이 조금만 있어도 옅게 빛나 판 전체를
덮는다. 문턱을 잡으려면 「퍼진 별빛」 격자의 통계(평균 또는 백분위수)를 커널에 넘겨야 한다.
발광성운 코드 자체는 `RenderField.cu` 의 가스 분기에 이미 들어 있다.

둘째, 밝기 대비다. 같은 파일에서 색과 밝기를 분리할 때 `const float tv = __fsqrt_rn(t)` 로
제곱근을 곱하는데, 실제 별의 광도 차이는 `M^3.5` 라 수천 배인 것이 수십 배로 압축된다.
그래서 사용자가 「입자들이 밝기의 차이가 거의 없다」고 알렸다. 제곱근을 넣은 이유는 색을
온도로 옮겼을 때 컬러맵이 깔고 있던 명도 바닥이 사라져 켜진 픽셀이 6.4%→1.34% 로
어두워진 것을 근사 복원한 것이다. 즉 「밝기 바닥」과 「밝기 대비」가 한 값에 묶여 있어
지수를 낮추면 대비는 살지만 화면이 어두워진다. 둘을 갈라라 — 대비는 실제 광도대로 두고
어두운 쪽 바닥만 따로 올리는 로그 톤 매핑이 맞다.

셋째, 블랙홀 운동량 보존이다. 블랙홀이 알갱이를 삼킬 때 질량만 늘고 **운동량은 버려진다**
(`kIntegrate` 의 `atomicAdd(&eaten[b], 1)` 자리). 그래서 판 전체의 운동량 보존이 깨지고,
동역학적 마찰이 없어 감속 기제 없이 중력으로만 계속 가속된다 — 사용자가 「블랙홀이 왜
이렇게 빠르게 날아다녀」, 「우주도 너무 빠르게 움직여」라고 알린 것이 이 뿌리다. 실측으로
정상 회전 속도가 0.25 인데 `maxSpeed` 가 1.7~2.9 로 7~12배다. 삼킨 운동량을 GPU 배열에
누적하고(`eaten[b]` 옆에 운동량 합 배열) 스텝 끝에서 호스트가 `v_new = (M·v_bh + m·v_p)/(M+m)`
로 반영하면 동역학적 마찰이 자연히 생긴다. 태어날 때 그 별의 속도를 이어받지 않는 것도
같은 자리에서 고쳐라 — 지금은 후보로 넘길 때 위치와 질량만 넘긴다. 이것을 고친 뒤에
시간 배율(현재 0.35, 은하 한 바퀴 187초)이 정말 빠른지 다시 판단하라. 지금 배속을 낮추면
이 증상이 가려져 원인을 찾기 어려워진다.

UI 전수조사는 앱 하단 툴바와 설정 보드의 모든 항목을 하나씩 실제로 눌러 보고 값을 바꿔
보는 것이다. 기능마다 ①실제로 동작하는가 ②동작이 표시와 맞는가 ③사용자 원칙(연출은
제거한다 · 원하는 것이 안 나오면 현실에 빠진 것을 찾아 더한다)에 걸리지 않는가를 보고,
안 되면 고치고 · 연출이면 지우고 · 물리가 틀렸으면 바로잡아라. 이미 하나를 찾아 뒀다 —
`ControlBridge.cpp` 의 `gridSize` 가 2D 시절 값만 받아 32/64/128 이 조용히 무시되던 것을
오늘 고쳤으니, 같은 성질의 버그가 다른 설정에도 있는지 특히 살펴라(밖에서 보낸 값이 코어에
닿는지 실제로 확인하는 방식으로).

검증은 동영상으로 한다. `ffmpeg` 가 설치돼 있으니 `-f gdigrab` 으로 **앱 창 영역만** 60fps
로 녹화하고, 프레임을 뽑아 한 장씩 정확히 봐라 — 대충 넘기거나 흐릿한 채로 판정하지
말고 각 프레임의 아홉 자리(위·왼쪽위·왼쪽·왼쪽아래·아래·오른쪽아래·오른쪽·오른쪽위·가운데)를
모두 확인하고 어느 자리에서 무엇을 봤는지 적어라. 스크린샷의 일부만 보고 판정하면 그 검증은
실패로 처리하고 다시 한다.

**녹화가 실제로 앱을 찍고 있는지 먼저 증명한 뒤에만 수치를 보고하라.** 오늘 바탕화면 캡처
24프레임·연속 1261프레임·영상 30초로 「검은 네모 0건」이라 보고했는데, `SetForegroundWindow`
가 조용히 실패해 Claude 창을 재고 있었다 — 사용자가 「영상에 앱은 안 보이고 클로드 대화내용만
저장돼있어」라고 알려 발견했다. 캡처가 대상인지 검증하지 않은 측정은 0 을 내도 아무 의미가
없다. `scratchpad\_win.ps1` 의 `Get-AppWindow`·`Test-LooksLikeApp` 이 그 검증을 한다
(창을 최상위로 고정하고 그 사각형만 캡처하며, 어두운 하늘인지 확인).

눈으로 보는 것과 함께 수치로도 재라. 색은 `scratchpad\hue.ps1`(색조·채도 기준 — 이전
`cyan.ps1` 의 R−B 기준은 사용자가 보는 것과 안 맞아 폐기했다), 격자 눈금은
`scratchpad\grid.ps1`(격자 주기 에너지 대비 주변 주기), 명멸은 `scratchpad\flick2.ps1`
(픽셀별, 판을 멈춘 상태와 도는 상태를 나눠), 안전은 `scratchpad\r55-all.ps1`(장면 4개 ×
10만·100만 전수) 를 쓴다. **수치가 통과해도 화면을 보고 판정하라** — 오늘 「따뜻한 색
59.96%」라고 보고한 화면을 사용자가 보고 「연한푸른색, 흰색, 검은색 이게 끝이야」라고 했다.

드라이버는 손대지 않는다(사용자 결정). 대신 재부팅 위험이 남아 있으므로 앱을 한 번에 길게
돌리지 말고 **30~45초 단위로 끊어** 녹화하고, 매 구간이 끝날 때마다 GPU 이벤트 로그를
확인하라(`Get-WinEvent -FilterHashtable @{LogName='System'; ProviderName='nvlddmkm'} -MaxEvents 5`
와 `Id=1001`). `nvlddmkm` Event 153 이 새로 찍히면 즉시 멈추고 보고한다 — 사흘 연속 그
신호 뒤에 재부팅됐다. 앱을 `Stop-Process` 로 죽이지 말고 제어 채널의 `cmd=quit` 로 보내
`Get-Process` 가 0 을 돌려주는 것까지 확인하고, 앱이 도는 동안 PowerShell 화면 캡처는
하지 않는다(캡처가 GPU 여유를 밀어낸다 — 실측: 캡처 없을 때 89 fps, 캡처 중 53 fps).
가설을 검증할 때는 파일을 고치기 전에 기준 상태를 확보하고, 검증이 실패하면 다음 가설을
세우기 전에 그 변경을 전부 되돌려라.

서밋·푸시·PR·파일 삭제·배포는 사용자 승인 없이 하지 않는다. 한 항목에 5바퀴를 돌고도
그 항목의 검증 기준을 못 채우면, 또는 전체 작업이 8시간을 넘기면 멈춰서 무엇이 되고 무엇이
안 됐는지 보고하고 확인을 받아라.
